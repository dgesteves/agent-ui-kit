Unified or split review of agent edits with word-level highlights and per-hunk accept and reject. Give it the old and new contents of each file, or a unified `patch` when you only have the diff, and it computes the hunks. J and K move between hunks, A and R decide (and move on), U resets, Shift A and Shift R decide everything, and ⌘ or Ctrl + Enter applies.

`onSubmit` receives each file with only the accepted hunks applied (`content`), with the ids of the hunks that were accepted, rejected or left pending; unreviewed hunks are left out of the content. That makes it a client-side tool result: send it back with `addToolOutput` and the agent continues from the files as you applied them, as [the quickstart](/docs/getting-started#render-a-run) does. It fires once per set of decisions: a double click or a repeated ⌘ or Ctrl + Enter sends one review until a decision or the files change. Files compare by content, so an inline `files` array does not re-arm it.

Large files stay responsive. A file that needs more than a few hundred edits is diffed in a worker, and reads "Comparing changes…" until it is done (Apply waits for it); the package's worker is emitted by webpack 5, Next.js and Vite without configuration, and `diffWorker` takes a function that starts your own, or `false` to diff on the main thread after the first paint. A file changed in more places than `maxEditLength` (2,000 lines added plus removed) is reviewed as one hunk that replaces the changed region, and the review says so. A long review renders only the rows near the screen: the rest keep their height and their text for screen readers, and every hunk stays in place for focus and J and K. [Performance and limits](/docs/limits) has the numbers.

The same work runs on the server too: `parseFileChange`, `applyHunks` and `computeReviewResult` are in `signoff-ui/core`, with no React. A server render diffs the files a render may diff and shows the rest as being compared, so hydration matches. Long changed lines skip word-level highlights rather than stall.
